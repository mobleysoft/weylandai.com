## Guest flow, 401 and demo isolation

`subx-app.html` calls `loadSessions()` at startup to discover an account's saved work. In a cold guest session its authentication probe returns 401, which `loadSessions()` explicitly handles by showing the guest upload/sign-in state. This request is expected in the current design; it is not a failed read, upload, or account requirement. No Rockford upload POST or Rockford `/doors` response appears in either guest traffic capture.

The homepage also intentionally creates an anonymous demo copy when its SubX chapter comes near the screen. Thus the demo POST and its 200 `/door-index` read (10 doors, 8 groups) are expected homepage background activity, not the uploaded job. The newer unmodified production journey allows that demo; the older Estimator journey explicitly intercepts and blocks demo creation. Neither should substitute the demo for the user's schedule.

There is no evidence of demo leakage into any check. Both guest exports contain precisely the 65 Rockford marks, no `D-101`/other demo marks, and matching Rockford cells. The saved packet uses this run's `user-sim schedule-plus-spec` session `f8a65a4d-f46b-4727-a2ba-6bdb18e3f307`, with 65 doors and 14 groups. Traffic includes the background demo but assertions select the workspace DOM/export or the uploaded project/session, not the unrelated door-index response.

The empty spec message is also not a race: `readGuest` assembles `guestDetail`, renders it, and returns before `finishUpload` reports completion. `renderDetail` writes exactly `hardware_schedule_needed.message` to `#hardware-needed`. The historical served-byte replay reproduces null without a browser, while the historical source replay produces the request.
