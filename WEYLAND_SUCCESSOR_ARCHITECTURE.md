# The weylandai.com successor architecture

**Status:** Design document — real target architecture, not yet built. Companion to `WORKER_MODULARIZATION_MAP.md` (the verified inventory of the current monolith this design is built from) and `WORKER_LESSONS_LEARNED.md` (why this is necessary). This is the document that should exist *before* more module code gets written, per direct instruction: stop hand-editing the legacy file, architect the real successor first.

**What changed from the plan in `WORKER_MODULARIZATION_MAP.md`:** that document's proposed layout (~86 `src/` files, esbuild-bundled back into one `weyland.worker.js`) was real progress — it gives every module a source of truth and clean boundaries — but it stops short of the actual goal. The end state isn't "one well-organized monolith." It's a collection of genuinely separate, independently deployable Cloudflare Workers (`weyland-<module>-module.worker.js`), the same way AuthFor and MASCOM_EDGE already exist as real separate services this worker calls out to today. weylandai.com's own internal complexity should follow the same pattern the rest of the conglomerate already uses correctly — that consistency is the point, not an aesthetic preference.

## Design principles

1. **Deflationary incubation model first.** No module in this design re-implements something a shared platform already owns. Where the current monolith built a local workaround (auth being the confirmed case — see below), the successor design routes through the real shared platform instead. A module Worker that duplicates AuthFor, MASCOM, or any other shared service is a design defect, not an implementation detail to fix later. **Billing is a second, real instance of this same problem**: per direct instruction, vendyai.com is supposed to handle all Stripe integration conglomerate-wide, but `weyland-billing.worker.js` (checkout, subscription, webhook) currently talks to Stripe directly via its own `stripeRequest()` helper. Unlike auth, this is NOT yet fixed and should NOT be migrated blindly — VendyAI's own Stripe integration was confirmed broken/fabricated as recently as 2026-08-26 (see memory), and there are currently three candidate VendyAI worker directories on disk (`vendyai-com-worker`, `vendyai-com`, and one explicitly named `...-DEAD-UNUSED-do-not-deploy`), the same confused-duplicate pattern already seen elsewhere in this portfolio. weylandai.com's own Stripe checkout is real, live, and revenue-generating today. Before any migration: audit VendyAI's actual current code with the same rigor applied to AuthFor (confirm which worker is really deployed, confirm its endpoints actually work, confirm its contract) — do not swap a working revenue path for an unverified one. Tracked as a real, high-priority open item, not silently assumed away.
2. **Worker boundaries are bounded contexts, not file boundaries.** The `src/` file-level split in the modularization map (~50 route files) is the right granularity for *readability*. It is the wrong granularity for *deployability*. Fifty separate Workers would mean fifty wrangler.tomls, fifty cold starts, and constant Service-Binding chatter between things that are actually one cohesive concern. Worker boundaries below are drawn at real bounded-context lines: does this cluster have an independent reason to scale, deploy, or be owned separately? If not, it's routes within one module Worker, not its own Worker.
3. **Explicit inter-Worker communication, no ambient state.** Every cross-module call is a real Service Binding (same-account, zero public network hop, the correct Cloudflare-native mechanism — confirmed weylandai-com-worker and authfor-gateway-worker are on the same account, no `account_id` overrides in either wrangler.toml) or, where genuinely cross-account, an explicit authenticated HTTPS call. Nothing is read from shared mutable module state the way `var cors` is today.
4. **Data ownership follows Worker ownership, with one honest near-term compromise.** In principle each module Worker should own its own tables. In practice, splitting the current single `weyland_db` D1 database into one-database-per-module now is a much larger migration (cross-module joins become cross-service calls, real data-migration risk) than the service-boundary work itself justifies as a first step. Near-term: one shared D1 database continues to exist, but each module Worker's code only ever touches the tables that belong to its bounded context — enforced by code boundary and review, not physical separation yet. Physical per-module database separation is a legitimate later step once the service boundaries have proven themselves in production, not a blocker to starting now. Stated as a real compromise, not silently assumed.
5. **No hard cutover, ever.** Every module ships alongside the existing monolith, verified against real request/response behavior, before the monolith's copy of that logic is deleted. The monolith shrinks route-by-route. This mirrors the safety discipline already established for hand-edits to this specific file (its near-miss data-loss history), applied at the service level instead of the line level.

## Proposed Worker boundaries

| Worker | Owns | Why this boundary |
|---|---|---|
| **`weyland-gateway.worker.js`** (the eventual, much-shrunk `weyland.worker.js`) | Top-level routing, the 36 marketing/product pages, `fetch`/`scheduled`/`queue` handlers, dispatch to module Workers via Service Binding | Public-facing pages need low latency and have little business logic — no value in a Service-Binding round-trip per page view. This is the "front door"; everything with real business logic behind it delegates out. |
| **AuthFor** (`authfor-gateway-worker` — already exists, not new) | All real identity: login, session issuance/verification, MFA, password reset | Nothing new to build here except making weylandai.com actually use it (see below). This is the flagship case of principle #1. |
| **`weyland-document-generators.worker.js`** | The 15 generate/download PDF routes + `renderHtmlToPdf`/`storeDocumentPdf` | Already confirmed fully isolated (map §4/§6) — no external callers, calls nothing product-specific elsewhere. Cleanest possible service boundary in the whole file. |
| **`weyland-sightx.worker.js`** | SightX routes, the `SIGHTX_ROOM` Durable Object, walkthrough-preview | Already has its own real-time/Durable-Object concern distinct from everything else — a natural, strong boundary that exists in the code today, not just on paper. |
| **`weyland-billing.worker.js`** | Checkout, subscription, the Stripe webhook | Map already flags the webhook as having a distinct trust boundary (Stripe signature verification) from the rest of billing — correct to isolate for independent review, and this is also where the real AuthFor-backed session-establishment fix lands (see below). **Should ultimately be a thin client of vendyai.com for the actual Stripe calls (principle #1), not this Worker's own `stripeRequest()` — deferred pending a real VendyAI audit, not yet started.** |
| **`weyland-hardware-schedule.worker.js`** | The 5-file hardware-schedule cluster (extract, candidates, page-review, export, affirm/submittal) | Real cohesive bounded context (~5,000 lines), coupled via D1 session state rather than JS references — safer to keep together than the file-level split implied. |
| **`weyland-cutsheet.worker.js`** | The 12-file CPS/cut-sheet cluster (match, enrich, catalogues, search, drafts, mappings, discovery, queue-admin) | The modularization map explicitly could not confirm these 12 files are safe as fully independent units — they share `PRODUCT_DATABASE`/`MFR_CODE_MAP`. One Worker with 12 internal route files is the honest boundary given that unresolved coupling; splitting further is a *later* question, not a blocker now. |
| **`weyland-takeoff-quotes.worker.js`** | Takeoff data/line-items, quote view/generate, pricing/resolve | Cohesive estimating-and-proposal vertical. |
| **`weyland-projects.worker.js`** | Projects CRUD, vendor-profile, sessions list/detail | Shared project/session data model underneath several other verticals — kept together to avoid premature fragmentation of state that's actually one concern. |
| **`weyland-hunt.worker.js`** | Hunt/opportunities, leads, quote-templates | Small, standalone product (HuntX) — real product boundary already exists at the marketing/pricing level. |
| **`weyland-device-auth.worker.js`** | Device pairing, bridge-launcher scripts | Niche, security-adjacent, worth isolating rather than folding into the gateway. |
| **`weyland-misc.worker.js`** | Chat, telemetry, market-signal stubs (pricex/marketx/compx/weatherx/forecastx/geox) | Explicitly a junk-drawer, named honestly as one rather than pretending these unrelated small stubs deserve their own Workers. Revisit once any of these stubs becomes real. |

Not eleven-plus Workers because eleven-plus was a target — because that's where the actual bounded contexts in the verified 260-route inventory fall. Contrast with the file-level plan's ~50 route files: most of those become routes *within* one of the Workers above, not each their own service.

## The auth fix, specifically (already in progress, this is its target shape)

Confirmed directly in the code (not assumed): today, no session in this worker is ever actually validated through AuthFor. Two session-creation paths exist — one authenticates against `auth-onamerica.ron-helms.workers.dev` (Ron's rejected fleet-auth mesh, not AuthFor at all), the other calls AuthFor's `/api/v1/register` as a side effect of a Stripe webhook and then self-mints a purely local session with zero further AuthFor involvement. The one real `AuthFor /api/v1/verify` call in the file sits behind both of these and is effectively unreachable in practice.

**Target shape:** there is no `weyland-auth-module.worker.js`. Identity is AuthFor's job, full stop — building a separate weyland-owned auth service would repeat the exact mistake this whole effort exists to correct. Instead:
- Every module Worker above that needs to know who's calling imports one shared, thin client library (`lib/authfor-client.js` — a library, vendored/shared across module Workers, not a deployed service of its own) that calls AuthFor's real endpoints (`/api/v1/login`, `/api/v1/sso/issue` + `/api/v1/sso/redeem`, `/api/v1/verify`, `/api/v1/refresh`) directly via Service Binding.
- `weyland-gateway.worker.js` (the login page) and `weyland-billing.worker.js` (the post-purchase session) are the two real integration points — both currently bypass AuthFor and both need the real fix, already scoped and in progress as of this writing.
- A local session cache (fast-path, avoids an AuthFor round-trip on every request) is fine to keep, but it must store/derive from something AuthFor actually issued and can invalidate — never a bare locally-generated UUID with no relationship to AuthFor, which is what exists today.

## Migration plan (strangler fig at the service level)

1. **Auth, first** — already the highest-priority fix in flight, and it's also the correct first *service* cutover: get `weyland-gateway.worker.js`'s login flow and `weyland-billing.worker.js`'s post-purchase flow both genuinely calling AuthFor for real, with the legacy local-only paths (Ron's mesh, self-minted UUIDs) removed once verified. This doesn't require the other module Workers to exist yet — it's a fix inside the current monolith's own auth logic, using the shared `authfor-client.js` library pattern this design settles on, so later module extractions inherit the correct pattern from day one instead of copying the broken one.
2. **`weyland-document-generators.worker.js`** — build as a real, separately deployed Worker (its own `wrangler.toml`, its own deploy). Add a Service Binding from the gateway to it. Add a route rule in the gateway that delegates the 15 document-generator paths to the binding instead of handling them inline. Verify identical behavior against real representative requests. Only then delete that logic from the monolith.
3. Repeat per Worker in the table above, roughly in order of isolation (document-generators → sightx → billing → hardware-schedule → the rest), same four-step pattern each time: build standalone and deployed → bind → delegate-and-verify → delete from monolith.
4. The monolith is "done" shrinking when `weyland-gateway.worker.js` contains only the 36 pages, top-level routing, and the cron/queue handlers that don't belong to any single module.

## What this document does not yet resolve

- Exact Service Binding wiring/wrangler.toml changes per module — real implementation detail for each step above, not decided in the abstract here.
- Whether `weyland-cutsheet.worker.js`'s 12 internal files can ever safely become independent services — explicitly deferred, not assumed either way.
- Physical D1 database-per-module split — deliberately out of scope for this phase per principle #4.
- **The VendyAI/Stripe migration itself** — principle #1 states the destination, not the plan. Needs its own real audit first: which VendyAI worker is actually deployed, does its checkout/webhook contract actually work today, what would weylandai.com's billing code need to change to call it instead of Stripe directly. Not started.
