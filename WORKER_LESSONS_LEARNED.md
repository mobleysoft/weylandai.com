# weyland.worker.js: what was wrong, what we fixed, and the standard going forward

This is a living document, not a one-time postmortem. Its purpose: a durable record of what "improper" looked like in the original build of weyland.worker.js, so any agent (human-directed or autonomous) working on this file or building something new for this estate can recognize the same failure modes early instead of repeating them. Update it every time the modularization effort finds another real defect or lands another real fix — don't let it go stale.

Companion documents: `WORKER_MODULARIZATION_MAP.md` (the structural audit and extraction plan this document's findings came out of) and `/Users/johnmobley/AGENTS.md` (cross-tool doctrine and incident log for the whole estate, not just this file).

## The root-cause finding: wrong dependency direction on auth

This is a violation of the conglomerate's **deflationary incubation model**: every venture's real work is supposed to make shared platforms (AuthFor, MASCOM, and whatever else gets built) stronger, so the marginal cost of the *next* venture keeps falling — not just solve its own local problem in isolation. Improving the conglomerate as a whole is the actual objective; improving one subsidiary in a way that leaves shared infrastructure untouched is, at best, only half the job. This is the headline finding, not one bullet among many. `weyland.worker.js`'s `authenticate()` function is not a clean AuthFor client — it's four different mechanisms layered together: a fully local `weyland_sessions` cookie-based session system that bypasses AuthFor entirely, a dead local-JWT path (the code's own comment admits nothing in the worker ever signs one), the one real AuthFor verify-and-bridge call, and unrelated signed-URL logic, all silently chained as sequential fallbacks with no separation.

The deeper problem isn't that this is messy — it's the direction it points. AuthFor is the conglomerate-wide shared identity platform, meant to serve every venture (weylandai.com, watchforce.cc, lawyik.com, and whatever comes next). Every time weylandai.com needed an auth capability and its builders reached for a local, bespoke answer instead of routing that real requirement into AuthFor, two things were lost at once: weylandai.com ended up depending on unshared, unaudited local auth surface area, *and* AuthFor never got hardened or extended by a real venture's real needs. Shared platforms only get better when the ventures that depend on them push requirements up into them. Building around AuthFor instead of through it means AuthFor stayed static while every venture that took the same shortcut accumulated its own parallel, unaudited auth code. This was the wrong approach from the first line of `authenticate()`, not a bug that crept in later — every other item below is a downstream symptom of the same instinct (solve it locally, in this file, rather than in the shared platform where it belongs).

## What was wrong, concretely (verified, not assumed)

1. **No source of truth for the majority of the backend.** `weyland.worker.js` is a pre-bundled esbuild output (confirmed via its `__esm`/`__commonJS`/`__toESM` bundler-runtime helpers) with no rebuild step at deploy time. Real esbuild-generated source stops at line 145,119 — everything after that (19,909 lines) is pure hand-editing with no module source anywhere. All backend/API business logic (260 routes) exists in exactly one place: the deployed bundle itself.

2. **22–24 of the 36 served pages have zero source outside the bundle**, not even covered by the partial `build.py`/`routes_manifest.json` system that regenerates the other ~18. This isn't drift from a source that could regenerate it — it's pages that were never captured in source form in the first place.

3. **A 5x-duplicated `ROUTE_LABELS`/`renderNav` block was a live navigation bug, not dead weight.** All five were `var`/`function` declarations in the same function scope; JS hoisting meant only the last (and smallest, 10-key) copy actually took effect for every one of the 36 pages served. 18 real, dispatchable routes had no nav link anywhere on the site as a result. Read as: five separate editing sessions each pasted the page-header boilerplate, unaware a previous copy already existed in the same scope. **Fixed 2026-09-09** — consolidated to one canonical copy (union of all 28 real keys across the 5 originals).

4. **A daily cron job called a function that was never defined.** `cleanupExpiredTokens(env2)` was invoked every day by the `scheduled()` handler and didn't exist anywhere in the file — a `ReferenceError`, silently caught and only logged, meaning password-reset-token cleanup had (as far as this code is concerned) never actually run. **Fixed 2026-09-09** — root cause traced to the auth problem above: the local `password_reset_tokens` table this was meant to clean up is never written to by anything in the worker, because the real password-reset flow already correctly delegates to AuthFor. The dead call was removed rather than "fixed" with a working query for a table that shouldn't exist as local state in the first place.

5. **`var cors` reassigned per-request as ambient module-level state**, read later by unrelated code paths (e.g. the top-level `fetch()` handler's catch block). Any code that needs `cors.corsify()` outside the request that set it is implicitly depending on a side effect from an unrelated code path having already run in the same isolate. A real blocker to clean module separation — flagged in the modularization map, not papered over.

6. **A near-miss data-loss incident** (documented separately in AGENTS.md, predates this specific effort): a naive string-search-based patch to this file once matched the wrong `</html>` delimiter 648,745 characters away and nearly deleted 13,829 lines. Caught and reverted, but it's why every edit to this file since has followed a strict verify-both-boundaries-with-line-numbers-first, `node --check`-after-every-edit protocol.

7. **`build.py` (the one real regeneration tool that exists) is itself flagged unsafe to run blindly** — its own docstring documents a real incident where it silently reverted 5 live pages by overwriting hand-patches that were never copied back into source. A symptom of the same root problem: when there's no reliable source of truth, even the tooling meant to help becomes dangerous to use casually.

8. **Frontend/backend contract drift caught live, not by design review.** SightX's floor-plan upload UI called `POST /api/sightx/reconstruct` — a route that didn't exist server-side (confirmed via a live `curl`, 404). The frontend had a real, working try/catch fallback to a cruder client-side heuristic, so this wasn't a hard user-facing break, but it meant the better-quality path was silently unreachable and nobody had verified it end-to-end.

## What we did about it

- **Read-only structural audit before any code changed.** `WORKER_MODULARIZATION_MAP.md`: inventoried all 260 API routes + 36 page routes, mapped shared/load-bearing dependencies (`authenticate`, D1, Stripe, R2), confirmed the ROUTE_LABELS duplication with exact line numbers, and proposed a concrete module layout — before touching a single line of the actual file.
- **Set an explicit design bar for what "modularized" has to mean**, per direct instruction: not just split into files, but small, single-purpose, obviously-named modules with explicit imports instead of ambient shared state — a stranger should be able to find something by name and change it with real confidence nothing else was touched. Every proposed module in the map is self-assessed against this bar, including the ones that don't yet meet it (flagged, not hidden).
- **Fixed both live bugs** (items 3 and 4 above) with the full safety protocol: git checkpoint before, precise line-verified edits, `node --check` after every change, `git diff --stat` to confirm the diff was scoped to exactly what was intended.
- **Started real extraction in the correct dependency order**: `authenticate()`/AuthFor logic first (the universal dependency — 216+ call sites — nothing else can be cleanly extracted around it), not because it's the easiest, but because every other module needs to import it explicitly instead of finding it ambiently.
- **Made the auth split honest instead of cosmetic.** The first extraction was redirected mid-flight: rather than relocating the existing four-mechanisms-in-one-function tangle into a file that would have been named `lib/auth.js` (which would have quietly formalized the local-session bypass as if it were just "the auth module"), the real AuthFor delegation and the local/legacy session-cookie path are being split into separately, honestly named modules — so the architecture problem is structurally visible in the file layout itself, not hidden under a reassuring generic name. The legacy local path is being preserved (not deleted) during this phase, since removing it is a real behavior decision that needs to be made deliberately, not as a side effect of a mechanical refactor.
- **Applied the same "don't build around the shared platform" correction to SightX.** A server-side `/api/sightx/reconstruct` endpoint was mid-build when the direction was corrected: SightX's wall-detection shouldn't depend on a server round-trip at all. Rather than adding more server-dependent surface area to an already-overloaded worker, the fix became a GOFAINEAT-evolved classifier — trained, verified offline, and running entirely client-side (99.47% held-out accuracy vs. 86.8% for the heuristic it replaced) — removing a server dependency instead of adding one.

## The standard going forward

- **The deflationary incubation model is the actual test for every change**: does this make the conglomerate as a whole stronger, or just this one subsidiary? A fix that only helps weylandai.com while leaving AuthFor (or whatever shared platform is relevant) untouched is an incomplete fix.
- Route real requirements into shared platforms (AuthFor, and whatever else the conglomerate builds) instead of solving them locally inside one venture's worker. If a venture needs an identity/auth capability that AuthFor doesn't have yet, that's a real AuthFor feature request, not a reason to build a parallel system.
- No new backend logic should exist only inside a deployed bundle with no source of truth. If it's not extractable to a real module with a real build step, that's a defect to fix, not a pattern to repeat.
- Module boundaries must be honest about what's actually happening in the code, not just organizationally tidy. Splitting code into files that hide an architectural problem behind a reassuring name is worse than leaving it in the monolith where at least it's visible.
- Every fix to this file follows the safety protocol above, without exception, regardless of how small the change looks — this file's history is the reason why.
